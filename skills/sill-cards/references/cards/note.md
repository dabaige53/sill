# note：笔记

保存用户自己的想法、记录、引文、X/Twitter 帖子和 Markdown 笔记。没有更明确的类型时用它。

示例是合成资料，只展示 `sill_createContent` 参数里外层的 `body` 对象，不能当作用户资料保存。通用要求见[类型索引](../types.md)，字段格式见[字段字典](../fields.md)。

## 显示

卡面：来源行（日期、阅读进度）→ 标题 → 摘要；`form:"quote"` 时标题显示为金句。详情：来源、标题、正文，不显示封面。

## 填写清单

| 字段 | 要求 | 怎么写 |
| --- | --- | --- |
| `title` | 必填 | 笔记的核心一句话；引文卡写引文本身 |
| `summary` | 必写 | 补充背景或为什么记下它，一句话 |
| `body` | 必填 | 笔记全文；帖子写原帖全文 |
| `form` | 引文时 | 引文、金句用 `quote`，其他省略 |
| `authors` | 有就写 | 引文或帖子的原作者 |
| `url`、`publishedAt` | 有就写 | 帖子地址和发布时间 |
| `tags` | 建议 | 主题词 |
| `sources` | 必写 | 用户口述写 `capture`，帖子写 `twitter`，文件写 `markdown` |

## 写法

标题写结论或观点，不写「笔记」「想法」这类空词。针对已有卡片的个人评论写 `state.note`，不新建笔记。

正文结构：

```markdown
核心观点一段。

## 依据

- 具体例子

## 下一步

要验证或要做的事
```

用户口述的内容保留原意，只整理语序和分段；不要扩写成文章。

## 示例

```json
{
  "type": "note",
  "title": "评审时先演示结果，再讲实现",
  "summary": "上周两次评审都卡在实现细节上，下次先给大家看用户能完成什么。",
  "body": "评审会的前五分钟决定了讨论方向。先演示用户能完成的事，大家讨论的就是体验；先讲实现，讨论就会陷进细节。\n\n## 依据\n\n- 周二的评审先讲了数据结构，40 分钟没谈到界面\n- 周四先演示了流程，15 分钟就定下了范围\n\n## 下一步\n\n下次评审把演示放在第一项。",
  "tags": [
    "评审",
    "工作方法"
  ],
  "sources": [
    {
      "name": "用户记录",
      "kind": "capture"
    }
  ]
}
```

## 写入前自检

- 标题是一个具体的观点
- 引文用了 `form:"quote"` 并写了作者
- 没有把对已有卡片的评论写成新笔记
