# 文件管理规范

更新：2026-10-29。文档按职责、预期稳定期和更新方式分四层；周期用于判断，不按到期时间自动迁移。决定依据见 [ADR 0088](../adr/0088-documentation-layers.md)。

## 1. 文档分层

| 层级 | 位置 | 内容与维护方式 |
| --- | --- | --- |
| 项目准则 | `docs/agent/` | 产品基本边界、开发、工程、事项、授权和文件管理规则；通常跨年度稳定，按明确决定更新原文 |
| 设计规范 | `docs/specs/` | 产品和系统应怎样设计；跨月、跨多个小版本稳定。总规范放根层，专题细则按需分目录 |
| 实现说明 | `docs/implementation/` | 当前实现、接口限制、平台差异及运行、测试、发布方法；随小版本同步更新 |
| 决策与专项记录 | `docs/adr/`、`docs/plans/`、`docs/records/` | ADR 按决定新增；专项计划工作期间更新，结束后原位标记完成；事件记录保留当时事实和证据 |

- 前三层维护当前正文，Git 保存历史。原文迁移、合并后只留一份正文，不另存旧版、日期版、备份版或链接壳。
- 适配 skill 或插件时，先查已有同类正文，再适配所需文件名；目录服从项目规则。工具无法发现时直接读取实际文件，不增设根目录副本。
- 文件改名、移动、合并和适配修改前，说明文件及影响并请求确认。当前请求已明确授权的范围直接执行，不扩大到其他文件。
- 前三层只写生效规则、当前行为和必要限制；删除过程、过期决定、逐次验收与修复备注留在 Git 或第四层。硬性禁止集中写在负责该规则的正文中。
- 现行文档发生冲突时，核对当前用户决定和实现；不以更新时间自动选择。已废止内容不作为当前要求。
- 通用检查标准放第二层，持续维护的当前差异放第三层，一次任务的检查结果放第四层。
- 通用执行要求直接维护在 `AGENTS.md`；专题定义、规则和例外在对应正文集中维护。关键边界可在 `AGENTS.md` 简明重申，修改时同步核对，避免产生不同版本。可直接查询的命令、版本和配置优先读取源文件，减少手工缓存。
- ADR 记录原因和替代关系，生效要求并入对应现行规范。历史更正说明原因，不把当时结果改写成当前结果。

## 2. 顶层目录

| 路径 | 职责 |
| --- | --- |
| `apps/web/`、`apps/apple/` | Web 与原生应用；Apple 共用代码放 `SillKit/`，端专属代码分开 |
| `server/local/`、`server/cloud/` | 本地服务与云端服务 |
| `contracts/` | 共享数据与接口定义、生成 Schema、合法及非法样例 |
| `design-system/` | 现有设计手册、变量、组件、画板、文案与素材；手册与可执行设计素材共同维护 |
| `docs/` | 项目文档 |
| `scripts/`、`tests/` | 构建、检查、生成脚本与可运行测试；各自 README 维护入口 |
| `deploy/`、`supabase/` | 部署配置与发布快照、数据库迁移 |
| `skills/`、`assets/` | 产品交付技能与品牌资产 |
| `.github/` | CI 与 PR 模板 |
| `.impeccable/` | 工具配置；运行时文件不提交 |
| `.agents/`、`.codex/` | 本地助手技能与环境配置；不存放凭据 |

根目录保留 `README.md`、`AGENTS.md`、`GLOSSARY.md` 和项目配置。产品、设计和 PR 正文分别位于 `docs/agent/PRODUCT.md`、`docs/agent/DESIGN.md`、`docs/agent/pr.md`。新增顶层目录或根文件时，先写 ADR，再更新允许列表。

依赖方向为 `apps/*`、`server/*` 引用 `contracts/` 与 `design-system/`，各端之间互不引用。具体代码规则见[代码规范](code-standards.md)。

## 3. 导航与命名

- `docs/README.md` 是总导航；现行文档列在其中，决策和事件分别按需进入各自目录索引。`AGENTS.md` 直接写明每次开发、优化都适用的规则与关键边界，专题细则使用按任务读取的入口；不得将其改成纯链接目录。
- 文件使用通用文档类型加明确主题。普通路径使用小写 kebab-case；工具或行业约定的 `README.md`、`PRODUCT.md`、`DESIGN.md`、`AGENTS.md`、`GLOSSARY.md`、`SKILL.md` 保留其名称。
- 前三层文档开头写更新日期和职责。日期只表示维护时间，不证明功能重新验证。
- ADR 使用 `docs/adr/NNNN-topic.md`，分配前核对最大编号；保留历史重复编号，不为整理目录重编号。
- 调试问题按[错误记录规范](error.md)维护；`docs/records/errors.md` 只做检索索引，具体诊断与证据归入对应事件目录。
- 产品版本变更汇总在 `docs/records/CHANGELOG.md`，未发布内容放 Unreleased；发布后写明版本、日期和平台范围，具体证据链接到事件记录。同版本补充部署按日期追加，不冒充新版本。
- 版权与授权正文只维护在 `docs/LICENSE`，项目入口引用该文件；授权方式或版权署名的变更须经权利人明确确认。
- 设计变更日志原位追加在 `docs/records/design-changelog.md`；它记录变更，不替代设计规范。
- 事件记录使用 `docs/records/YYYY-MM-DD-topic/README.md`，结果与附件同目录；相关专项计划在 `docs/plans/` 原位维护，不复制成另一份计划。
- 版本范围由 GitHub milestones 管理，不按产品版本号新建规范文件夹。普通文件不用 final、latest、new、备份等后缀。
- 业务术语见根目录 [GLOSSARY](../../GLOSSARY.md)。文档分层术语在本文维护，不写入业务术语表。

## 4. 移动与整合

先确认目标与范围，再移动或合并已有正文，同步更新导航、Markdown 链接及代码中的文档路径。历史记录只修正导航，保留原日期、结论和历史原路径。混合文档中的独有事件事实可分离为记录，已存在的证据不重复复制。

迁移完成时，原路径不留副本或符号链接；应保留的独有内容有明确去向；新链接可用。无法确认归属或是否重复的材料先列出，不自动删除。

## 5. 源文件、产物与证据

- 构建产物统一到 `dist/<端>/`，不手改产物、发布快照或生成文件。发布快照位于 `deploy/releases/YYYY-MM-DD-<端>/`，既有快照保持原样。
- 数据与设计定义从源文件生成；共享 Schema 提交并检查一致性，Apple 生成类型与 String Catalog 不提交。产品版本只维护于 `package.json`。
- 文案源在 `design-system/copy/zh-Hans/`，设计变量源在 `design-system/tokens/`；生成流程见设计系统与脚本目录。已执行数据库迁移保持原样。
- 测试产物保留在被忽略的 `tests/artifacts/`；有长期证据价值时，审阅后纳入对应事件目录。移交证据不等于复制规范备份。
- 文档目录不提交打包文件；单个证据文件不超过 2 MB，超出时压缩媒体或用截图加步骤说明，不使用 Git LFS。
- 提交前去除 token、授权码、个人内容和浏览器存储。

## 6. 数据与清理

- 本地卡片、Mac 数据与云端账号数据各守数据边界。Git 不是用户数据备份；本地数据、凭据、缓存与产物不提交。
- 秘密通过安全配置提供，示例只写变量名。不得进入文档、卡片、模型上下文、日志和浏览器持久化存储。
- 移动用户数据前停止写入，保留仓库外数据副本并验证读取，再按授权替换。该数据保护规则不适用于复制文档旧版。
- 清理失效规范时用 Git 保留版本；独有决策和证据先明确去向。用户数据、历史证据、迁移和发布快照不按时间自动删除。
- 不再使用的代码按既有移除流程处理，保留必要恢复点和删除记录；不建立废弃代码备份目录。

## 7. 检查

交付前运行 `npm run files:check` 并检查 `git status --short`。检查覆盖目录归属、现行日期与导航、链接、证据大小、依赖方向和本地文件隔离。实际检查范围按[测试规范](test.md)执行。
