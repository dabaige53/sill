# 云端首次加载的保存状态（C1 补充）

日期：2026-10-19。补入原 [C1 PR #48](https://github.com/dabaige53/sill/pull/48)，不另开同一工作包的 PR。U5 的 CI 在 `cloud-operations-browser.ts` 等待保存状态时超时；U5 基础 `46565cf`、当前 `3b15075` 在本机同一位置均失败。产品修复基准为 C1 的 `4aad866`。Mac 未改。

## 原因与修复

`adoptWorkspace()` 已接收服务端工作区并建立保存基准，但没有调用 `syncStatus()`。新的页面中没有 `data-sync` 属性。若用户打开的是已看过的卡片，`seen:true` 没有变化，不会产生保存请求，也不会间接更新该属性，原有保存等待便不会结束。示例卡片同批创建、按时间和随机 ID 排序，可解释此前有时通过、有时超时。

临时诊断实际读到：预览已打开，grid 仍连接在页面上，卡片 30 张，所有 `[data-sync]` 节点为空，页面异常为空。见 [观测](diagnostic.json)。这证明缺少初始状态，不表示保存请求失败。卡片顺序影响偶发结果的解释来自现有排序与无变化写入路径。

修复仅在 `adoptWorkspace()` 采用工作区后调用一次既有 `syncStatus()`。没有新增网络请求、持久化、界面控件、文案或公开方法；错误与待保存状态仍由既有逻辑决定，不直接写死为 saved。

## 回归证据

先新增检查，再运行原实现：登录并重新加载后，在任何写操作前等待初始 saved；原实现稳定超时，见 [新增回归改前](before.log)。原有会话过期、未知结果、冲突及保存等待全部保留，没有延长等待、删断言或绕开失败。

新增检查还会把主题偏好设成原值，等待两次浏览器绘制后确认状态仍为 saved、没有新增保存请求；在会话清理循环的每次重新加载后再次检查 saved。补一行状态初始化后，完整云端操作浏览器流程通过，见 [修复后](after.log)。原 U5 CI 及基础复跑日志分别保存在 [CI 失败](ci-failure.log)、[基础失败](base-failure.log)、[U5 当前失败](current-failure.log)。

源码与回归提交后运行完整 Node、云端构建及相关云端浏览器检查，最终结果以 PR Evidence 为准；此目录中的 before/after 指同一回归在修复前后的本地实测，不代替最终 CI。
