# Web 与 Mac 整库处理与加载优化

## 问题与状态

状态：Web 已修复待验证；Mac 已修复待验证（本机无法编译 Swift）。最近检查：2026-11-08。

用户反馈 Web 与 Mac 仍有加载慢、运行卡的问题，要求减少一次性加载。源码排查找到五处随卡片总量变慢的做法：

1. Web 每次操作（收藏、勾选、读文章时每 5 秒的阅读计时）都把全部卡片复制、比较一遍，保存回执后再全部重建一遍。
2. Web 每次渲染卡片列表、每次搜索按键，都把每张卡的正文重新解析一遍。
3. Web 页面误把服务端用的校验库 zod 整个打包进来（压缩后约 86 KB），每次打开都要下载和编译。
4. Mac 每 5 秒的刷新不带修订号，每次都下载整个工作区（含全部正文），并解析两遍。
5. Mac 每次写入前先完整读取一次工作区，写入回执又是整库，一次写入两次整库传输、三次整库解析；写入期间该卡片的按钮锁定。

## 环境与触发

- 源码基准：`9f6a547`（1.2.37）。本次是源码排查与合成数据测量，未使用真实账号。
- 测量环境：Linux 容器 Node 22，合成工作区 300 张卡（正文约 150 万字符）与 1000 张卡（约 500 万字符），每张卡含中英文 Markdown 正文；数据形状与云端读取接口一致。手机与旧电脑的耗时通常是这里的数倍。
- 触发：账号卡片越多、正文越长越明显；读长文时每 5 秒出现一次。

## 定位依据

**Web 每次操作整库处理（测量证实）**：`cloud-entry.ts` 把 `Store.save` 接到 `CloudSync.capture`。每次保存时 `workspaceState()` 对每张卡调用 `cloudCard()`（深拷贝并在缺摘要时解析正文），`CloudSync` 再把整个工作区序列化复制成新基线；回执由 `adoptWorkspace()` 处理时又对全部记录调用 `cloudCard()`、再算一次 `workspaceState()` 并复制。服务端每次保存都返回完整工作区（`sill_apply_operations` 末尾调用 `get_workspace()`）。

| 300 张卡，每次 | 耗时中位数 |
| --- | --- |
| 保存前整库投影 `workspaceState()` | 25.6 ms |
| 新基线深拷贝 | 7.6 ms |
| 回执后 `cloudCard()` 全部重建 | 28.8 ms |
| 回执比较界面状态 | 7.4 ms |

合计每次操作约 100 ms 主线程时间；1000 张卡时超过 300 ms。

**Web 渲染与搜索重复解析正文（测量证实）**：卡片来源行的阅读时长 `cardReadingTime()` 每次渲染都用 markdown-it 解析整篇正文；搜索 `matches()` 每次按键对每张卡解析正文再拼接，一次按键还会经过信息流、建议列表和类型标记三次筛选。300 张卡时渲染 40 张卡的阅读时长 13.5 ms，搜索一次筛选 57.8 ms；1000 张卡时搜索一次筛选 186.8 ms。

**Web 包含 zod（构建证实）**：代码规范要求 Web 不打包 zod。按模块统计云端构建，zod 占约 16 万字符。两条入口：Web 从 `contracts/appearance.ts` 读取排版默认值，而该文件顶层创建 zod 枚举；卡片写入校验经 `card-rules.ts` → `card-metadata.ts` 使用 `card-rich.ts` 里的纯规则函数，而该文件顶层定义 zod 字段。打包工具无法剔除顶层调用，整个 zod 被带入。

**Mac 定时整库下载与写入前整库读取（源码证实）**：`SillKit/CloudWorkspace.swift` 的 `read()` 不带 `X-Sill-Revision`（2026-10-29 只改了 Web，见[跨端性能优化](../2026-10-29-performance/README.md)）；`apply()` 开头调用 `fetchWorkspace()` 取核对基准。`CloudWorkspace.state()` 校验解析一次快照后丢弃，`CloudBackend` 又解析一次。每张卡解析要校验并编解码四次（`Card.init(json:)`）。2026-11-05 的追踪中出现过 1231 ms 的刷新读取，见[Mac 打开长文卡片卡顿](../2026-11-05-macos-long-article-open/README.md)。

## 处理情况

Web：

- 正文派生文本按正文缓存：新增 `atoms/text-memo.ts`，Markdown 纯文本与首段摘要（`atoms/markdown.ts`）、阅读分钟数（`data/card-source.ts`）每篇正文只算一次；超过约 800 万字符时淘汰最久未用的。
- 搜索文本按卡片缓存：`cardSearchText()` 与 Mac `CardModel.searchText` 对应，标题、摘要、来源、备注、正文、标签任一变化即重建；匹配结果与原拼接方式相同。
- 保存不再整库处理：回执中内容未变的记录沿用原对象（`keepUnchanged`），每条记录的界面卡片只投影一次（`projectedCard`），未被页面替换的卡片保存时直接用记录本身（`storedCard`）；`CloudSync` 基线共享卡片对象，只复制个人状态与偏好。
- 去掉 zod：`contracts/appearance.ts` 改为纯数据，schema 字段在 `local.ts` 生成；`card-rich.ts` 的纯规则函数移到 `card-metadata.ts`。生成的 schema 不变。Web 构建新增检查，zod 再进入包时构建失败（`web_bundle_includes_zod`）。

Mac：

- `CloudWorkspace` 保存最近一次读取或写入结果；定时读取带修订号，服务器答复未变化时直接沿用，不下载卡片也不重新解析。
- 写入的修订号与最近结果一致时，以该结果作核对基准，不再先整库读取；不一致时照旧读取。
- 解析好的快照随结果传给 `CloudBackend` 与 `Account`，不再解析第二遍。
- 云端快照修订号与当前显示一致时，`Workspace` 不再做差异计算。本地数据目录模式照旧比较，因为外部工具改 `cards.json` 不一定提升修订号。

取舍与风险：

- Web 的复用依赖“卡片对象只整体替换、不原地修改”。现有代码检索未发现原地修改；约束已写入 [Web README](../../../apps/web/README.md)。
- Mac 常驻多保存一份最近工作区（服务器原始 JSON 与解码后的卡片），约为正文总量的两倍。
- “修订号相同即内容相同”：服务端部署若改变输出格式而未提升修订号，界面在下一次真实变化前仍显示旧格式（Web 自 2026-10-29 起相同）。若恰在此时写入回执丢失，结果核对可能判为“结果未知”，重新打开应用后恢复。

未处理（需另行决定）：

- 服务端每次保存都返回并在幂等回执中保存完整工作区。Web 读文章时每 5 秒的阅读计时仍会下载一次整库，客户端处理已降到毫秒级，但流量未减。需要数据库迁移与两端同时改为只返回变化或修订号。
- Web 每 5 秒的检查是两次请求（会话与工作区）。
- Web 是单个内联 HTML（云端约 1.34 MB，gzip 约 443 KB），详情、设置、AI 等模块无法按需加载；拆分涉及 Worker 托管、MCP 单文件页面与缓存策略。
- Mac 瀑布流仍不是懒加载（见[Mac 卡片列表滚动卡顿](../2026-11-03-macos-feed-scroll/README.md)）；快照解析每张卡仍有四次编解码。

## 验证与后续

本地检查（2026-11-08）：

- 同一合成数据改后复测（300 张卡）：保存前采集 0.5 ms（原 35 ms）；回执处理含 JSON 解析 5.2 ms（原约 72 ms，其中解析 2.6 ms）；渲染 40 张卡阅读时长 0.01 ms（原 13.5 ms）；搜索一次筛选 0.6 ms（原 57.8 ms）。1000 张卡：采集 1.8 ms、回执 22.6 ms、搜索 1.9 ms（原 186.8 ms）。这些是脚本测得的计算时间，不是界面帧率。
- 云端页面构建（UTF-8 字节）1,426,693 → 1,340,944，gzip 466,704 → 442,663；本地页面同样少约 86 KB。改前数字取自同一提交的临时工作树。
- Web 相关单测 27 个文件共 305 项通过：Markdown、卡片内容与元数据、云端卡片与同步、会话视图、搜索、导航、设置、选择、提醒等，含新增 `tests/web/text-memo.test.ts` 与云端卡片、同步的回归项；撤掉正文缓存时“正文只解析一次”一项失败。契约检查与 59 项契约及服务端测试通过；`tsc --noEmit` 通过；Biome 无错误。未运行完整 `test:core` 与浏览器测试。
