# 手机抽屉 touchCancel 用例偶发失败

## 问题与状态

状态：已修复待验证，原因已定位。本地检查已通过，还需要在 GitHub Actions 的后续运行中确认。最近检查：2026-11-08。

## 环境与触发

- 入口：`tests/e2e/motion-material-browser-material-focus.ts` 的 `Real touchCancel keeps the drawer open without writing`，在 `web / browser (motion)` 中运行。
- 报错原文：`cancel restores the drawer position`。
- 触发：机器繁忙时，抽屉动画开始或结束得晚，超过用例固定等待的 600ms。

## 定位依据

- 已证实：这是测试的时序问题，不是产品缺陷。本地用合成卡片和 CPU 降速跑了 72 次，抽屉最终都回到原位，弹窗一直开着。
- 已证实，开场量早：4 次在 600ms 时抽屉离静止位置 24 还很远（232、623、623、844），都是该进程第一次打开抽屉；844 表示进场还没开始。
- 已证实，结尾量早：取消后 159ms 仍在 87，733ms 才到 26.3。
- 观察：提交 `1edf92dd` 在 main 的 CI `42456708361` 和发布流程第 2 轮都通过，只有发布流程第 1 轮失败。那次失败截图中抽屉顶部约在 76，符合复位还没走完。
- 观察：1.2.35 的正式流程 `41975795539` 也因同一用例失败过，当时没有保留位置数据，无法确认是哪一种。

## 处理情况

- 只改用例，不改产品代码。固定等待改为轮询：先等抽屉落定，再等拖动生效，最后等它回到原位，每步最多 10 秒。
- 新增前置断言：拖动必须真的让抽屉移动，避免复位检查什么都没验证。
- 单纯并行加压不能区分新旧写法：旧写法并行跑 16 次全部通过。
